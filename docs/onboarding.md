# Підключення нового клієнтського сервера

## Один раз на центральному ServerWatch

Для майстра потрібен робочий публічний HTTPS із довіреним сертифікатом. Домен
не обов’язковий: підійде HTTPS на IP за [ip-https.md](ip-https.md). Клієнт повинен
мати вихід на центральний HTTPS:443, а центральний VPS — доступ до SSH-порту клієнта.
Один лише локальний HTTP через SSH-тунель для callback не підходить.

В `/etc/serverwatch/serverwatch.env` задайте базову адресу **центральної панелі**,
наприклад `PUBLIC_BASE_URL=https://92.5.162.96`. Адреса без `/login`, логіна, пароля,
query та fragment. Не змінюйте SECRET_KEY і ENCRYPTION_KEY.

Після оновлення коду зупиніть три процеси й застосуйте готову міграцію
`4e2c9d8f610a` за розділом «Оновлення» README. Не запускайте повторну генерацію
environment і не використовуйте `db.create_all` або `stamp head`.

```bash
sudoedit /etc/serverwatch/serverwatch.env
sudo systemctl stop serverwatch-web serverwatch-bot serverwatch-monitor
sudo /opt/serverwatch/.venv/bin/python /opt/serverwatch/scripts/manage.py upgrade
sudo systemctl start serverwatch-web serverwatch-bot serverwatch-monitor
sudo systemctl is-active serverwatch-web serverwatch-bot serverwatch-monitor
```

Міграція зберігає попередні ключі, групи й дані. Уже підключені сервери продовжують
використовувати свої облікові записи й перевірений `known_hosts`. Їм не потрібно
повторно запускати скрипт. Нові сервери використовують індивідуальне закріплення
host key у БД, тому ручний `known_hosts` для них не потрібен.

## Крок 1: створення запису

У панелі відкрийте **Сервери → Додати сервер**. Вкажіть назву, публічну IPv4,
SSH-порт, клієнта й інтервал. Поле користувача встановлення — ваш адміністративний
SSH-логін на клієнті: `root`, `ubuntu` або інший користувач із sudo.
Це не логін фонового моніторингу: для нього скрипт створить `monitor`.
Telegram Group ID можна залишити порожнім — бот заповнить його після `/bind`.

Укажіть потрібні systemd-unit, наприклад `nginx.service, mysql.service`.
Необов’язкова опція SWAP встановлює лише контрольований helper і вузьке sudo-правило;
сам swap під час підключення не створюється. За замовчуванням ця опція вимкнена.

Натисніть **Створити сервер**. Python генерує окремий Ed25519 для цього запису.
Приватний ключ шифрується Fernet у пам’яті й залишається тільки на центральному
сервері. Панель, API та клієнтський скрипт його не отримують.

## Крок 2: один готовий скрипт

Натисніть **Скопіювати весь скрипт** або **Завантажити .sh**. Це персональний
скрипт із секретним токеном на одну годину. Він показується лише під час випуску.
Після оновлення сторінки можна випустити новий; попередній токен анулюється,
а пара SSH-ключів зберігається. Збережений `.sh` не публікуйте й видаліть після
завершення. Вставлений скрипт вимикає Bash history для поточної сесії, але не
приховує текст від запису термінала або буфера обміну.

На своєму комп’ютері підключіться звичайним адміністративним SSH до **клієнта**.
На Windows це також можна зробити в CMD або PowerShell; вставляти скрипт потрібно
вже в Linux Bash на клієнті. Вставте весь скрипт або запустіть завантажений файл
через `bash serverwatch-ID.sh`. Вручну редагувати його не потрібно. Для користувача
з sudo термінал може запитати його пароль.

Підтримуються Ubuntu/Debian із systemd, Python 3 та OpenSSH. Скрипт:

- Перевіряє root/sudo й встановлює відсутні залежності.
- Створює `monitor` або перевіряє придатність наявного облікового запису.
- Ставить root-owned dispatcher і збирач у `/usr/local/lib/serverwatch/`.
- Додає публічний ключ із `restrict,command="/usr/local/lib/serverwatch/ssh_dispatch.py"`.
- Створює окремий непривілейований `serverwatch-terminal` для браузерного SSH PTY.
- Встановлює точні sudo-правила для можливостей, вибраних у майстрі.
- Зберігає сторонні рядки `authorized_keys`, не додає дублікати й перевіряє права.
- Перевіряє `sshd -t`, читає лише **публічний** host key і надсилає його через HTTPS.

Глобальний `sshd_config` та інші SSH-логіни не змінюються. Для системних подій
`monitor` отримує читання групи `systemd-journal`, якщо вона існує. Передаються
класифіковані події, а не сирі MESSAGE. Наявний привілейований monitor або monitor
із nologin/false викликає зрозумілу помилку; сторонню конфігурацію скрипт не виправляє.

Ключ `monitor` запускає dispatcher із фіксованими операціями. Окремий ключ
вебтермінала дозволяє PTY для свого SSH-акаунта. Для конкретного сервісу
перезапуск потребує окремих точних правил sudoers. [Налаштування операцій VPS](vps-operations.md).

Наприкінці скрипт повідомить, що центральний worker перевіряє SSH. Поверніться
до відкритої сторінки майстра. HTTPS callback лише закріплює host key й ставить
перевірку в чергу: **READY з’явиться тільки після фактичного SSH-збору метрик**.
Майстер сам оновлює стан й відкриває третій крок.

## Крок 3: Telegram

Панель покаже окремий 15-значний код на 24 години. У БД залишається тільки HMAC;
код одноразовий. Додайте бота до групи й від головного Telegram-адміністратора
надішліть `/start`, потім **одним повідомленням** `/bind ВАШ_КОД`.
Команда `/bind` працює і з privacy mode, коли звичайні повідомлення з цифрами бот
може не бачити. Код встановлення й Telegram-код — різні секрети.

Після підтвердження групи стан стане **ACTIVE**. Надішліть `/status` та `/report`;
перевірте актуальний час метрики. `/report` може спочатку показати останній знімок,
потім підтвердити запит перевірки й надіслати свіжий звіт. Перегляньте графіки
на детальній сторінці сервера.

## Стани й повторна спроба

| Стан | Що відбувається |
|---|---|
| PENDING_SETUP | Скрипт випущено, очікується запуск |
| INSTALLING | Клієнт підтвердив початок встановлення |
| VERIFYING | Callback прийнято, worker перевіряє SSH і метрики |
| READY | Моніторинг перевірено, підключіть Telegram |
| ACTIVE | Підключені SSH і Telegram |
| INSTALLATION_FAILED | Скрипт завершився помилкою або токен прострочений |
| CONNECTION_FAILED | Центральний VPS не зміг підключитися або отримати метрики |
| DISABLED | Моніторинг вимкнений адміністратором |

Якщо токен прострочений або скрипт перервався, випустіть новий у майстрі й повторіть.
Повторне виконання вже завершеного скрипта відхиляється за використаним токеном
до змін клієнта. Новий скрипт з тим самим ключем не дублює `authorized_keys`.
Якщо callback загубив відповідь, спочатку перевірте стан панелі: він міг уже
прийняти запит і почати SSH-перевірку.

При CONNECTION_FAILED перевірте SSH-порт у панелі, firewall клієнта та мережеві
правила провайдера. Панель показує безпечну причину, journald — клас помилки без
секретів. При зміні host key автоматична заміна заборонена: перевірте справжність
сервера через незалежну консоль перед адміністративним відновленням прив’язки.
Не вимикайте TLS або перевірку SSH-ключів заради продовження.

## Перевірки реалізації

Тести використовують SQLite, mock SSH і mock HTTPS. Вони охоплюють генерацію
ключів, протокол dispatcher, callback, перевірку метрик, статуси, повтори,
прострочення, CSRF, Telegram та міграцію. Реальний root-інсталятор на клієнті
автоматичні тести не запускають. Перед production перевірте один тестовий
Ubuntu/Debian-клієнт і цільову MySQL за описаними трьома кроками.
